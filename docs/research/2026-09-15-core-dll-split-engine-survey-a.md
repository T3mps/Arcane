# Engine Survey A: Core/Client/Server DLL Split, Embedded Server Worlds

Public-source research only (official repos + docs; Source material limited to public `ValveSoftware/source-sdk-2013`). `.example/` (local Unreal dump) is out of scope — UE is covered in `2026-09-15-core-dll-split-ue-inspiration.md`. Every claim is cited `repo:path:line` (or symbol) or a doc URL; unverified claims are marked **not found**. Context: Arcane's proposed split is `ArcaneCore.dll` (headless: scene, physics, project, serialization, sim, jobs, plugin host, logging, a headless `Runtime` world facade) + `ArcaneClient.dll` (presentation, links Core) + `ArcaneServer.exe` (Core only) + an editor linking both, wanting an **embedded server world** alongside its own world, same game module, one process. No recommendation — nine engines' shapes as found, a comparison table, then an inventory of the distinct shapes in use.

---

## 1. Godot 4 (`godotengine/godot` @ `4.4-stable`; LibGodot @ `master`)

1. **Split**: monolith, one `godot` exe per platform SCons target (`platform/windows/SCsub:60`); editor-vs-game is a compile-time `target` flag (`SConstruct:63,161,467`). Globals are static-pointer singletons: `Engine` (`core/config/engine.h:41,94,106`), `OS` (`core/os/os.cpp:774-776`), `SceneTree` (`scene/main/scene_tree.cpp:1841-1844`). Only shared-lib boundary is GDExtension, one C-ABI `entry_symbol` (`core/extension/gdextension_library_loader.cpp:219-284`).
2. **Game unit**: no module concept — engine classes register once via `register_*_types()` (`main/main.cpp:684,715,738`), GDExtension classes register once into a process-wide map (`core/extension/gdextension.cpp:399-456`); all instanced per scene under the one `SceneTree`.
3. **N worlds**: no — one `SceneTree` as the process `MainLoop` (`main/main.cpp:3896,3970`). Multi-instance/PIE spawn **separate OS processes** via `OS::create_instance()`→`create_process()` (`core/os/os.h:195`; `editor/run_instances_dialog.cpp:167`); the 4.3+ embedded Game view still spawns a child and reparents its window (`main/main.cpp:1799-1808`).
4. **Role/authority**: per-`Node` authority id (`scene/main/node.h:200,729-731`) vs. a `MultiplayerAPI` scoped per node-subtree (`scene_tree.cpp:1622-1690`); `is_server()` = unique_id == `TARGET_PEER_SERVER` (`scene/main/multiplayer_api.h:76`).
5. **Dedicated server**: same binary, runtime `--headless` selects `DisplayServerHeadless` + null audio (`main/main.cpp:1332-1335`; `servers/display_server_headless.h:38-52`); same main loop.
6. **Hot reload**: GDExtension only, opt-in (`is_reloadable`, `gdextension_library_loader.cpp:370`), requires `recreate_instance_func` or is disabled (`gdextension.cpp:412-415`); refuses parent-type changes (`gdextension.cpp:390-396`); snapshots `PROPERTY_USAGE_STORAGE` per `ObjectID` across reload (`gdextension.cpp:863-990`). LibGodot (`master`, PR #110863) adds `GodotInstance` wrapping `Main::setup2/start/iteration`; true N-instances-per-process support is **not found** (still layers on the same static `OS`/`Engine` singletons).

## 2. Bevy (`bevyengine/bevy` @ `v0.14.0`; `simgine/bevy_replicon` @ `v0.44.1`; `cBournhonesque/lightyear` @ `main`; `lee-orr/dexterous_developer`)

1. **Split**: facade-of-crates, feature-gated, no `bevy_server` crate (`crates/bevy_internal/Cargo.toml`). Normally one static binary; `dynamic_linking`/`bevy_dylib` is a build-speed-only dylib, explicitly not hot reload (`crates/bevy_dylib/src/lib.rs:7-15`). Globals: task pools (`crates/bevy_tasks/src/usages.rs:6-75`) and an atomic `WorldId` counter (`crates/bevy_ecs/src/world/identifier.rs:22-34`) — the component registry itself is per-`World`, not global.
2. **Game unit**: `Plugin::build(&self,&mut App)` (`crates/bevy_app/src/plugin.rs:58-93`) registers into an `App`/`SubApp`; `World` (`crates/bevy_ecs/src/world/mod.rs:109-179`) is a plain value holding its own `Components` table (`crates/bevy_ecs/src/component.rs:598-602`).
3. **N worlds**: **yes** — `App` wraps `main: SubApp` + `sub_apps: HashMap<...,SubApp>` (`crates/bevy_app/src/app.rs:112-127`; `sub_app.rs:59-97`), doc'd for "processes... kept separate," not render-specific. lightyear's "host-server" mode instead **collapses** client+server into ONE World (`crates/connection/connection/src/host.rs:1-2`; proof at `crates/tests/src/stepper.rs:433-453`). bevy_replicon examples use one `App`, role via resource presence at CLI parse (`example_backend/examples/tic_tac_toe.rs:97-127`) — no two-App example found.
4. **Role/authority**: bevy_replicon — per-App `ClientState`/`ServerState` (`src/shared/backend.rs:41-66`); `ClientId::Server` = listen server (`src/shared/client_id.rs:12-17`). lightyear — per-**entity** markers `HostClient`/`HostServer` (`crates/connection/connection/src/host.rs:32-43`).
5. **Dedicated server**: `MinimalPlugins` (`crates/bevy_internal/src/default_plugins.rs:183-218`) vs. feature-gated `DefaultPlugins` (`bevy_winit`/`bevy_render`, root `Cargo.toml:55-81`). `ScheduleRunnerPlugin` replaces the winit loop (`crates/bevy_app/src/schedule_runner.rs:34-172`; example `examples/app/headless.rs:11-27`).
6. **Hot reload**: 3rd-party only. `dexterous_developer` reloads opted-in `reloadable_scope!` systems/components/resources, state via `rmp_serde`; ECS hooks/observers unsupported (README). `hot_lib_reloader` swaps `#[no_mangle]` functions but warns shared-type layout changes and `TypeId` reliance (i.e. Bevy's ECS) "face challenges" post-reload (README).

## 3. O3DE (`o3de/o3de`, `development` @ `b374579`)

1. **Split**: static `AzCore`/`AzFramework`/`AzGameFramework` + per-domain Gem DLLs (collapsed to static libs under `AZ_MONOLITHIC_BUILD`, `Code/Framework/AzCore/AzCore/Module/Module.h:84-105`). A Gem exports four C-linkage entry points (`AZ_DECLARE_MODULE_CLASS`, `Module.h:89-104`). Cross-DLL globals: `AZ::Environment` (GUID-keyed, must be attached per module, `AzCore/Module/Environment.h:34-113`) and `AZ::Interface<T>` — **one slot per type per Environment** (`AzCore/Interface/Interface.h:11,26-32`).
2. **Game unit**: one Gem compiled into role-specific variants (`Multiplayer.Client/.Server/.Unified.Static`, `Gems/Multiplayer/Code/CMakeLists.txt:25-238`), selected per **launcher target** (`Code/LauncherUnified/launcher_generator.cmake:221,281,347`). `IMultiplayer`/`INetworkEntityManager` registered once via `AZ::Interface<T>::Register()` (`Gems/Multiplayer/Code/Source/MultiplayerSystemComponent.cpp:240`) — one process-wide instance.
3. **N worlds**: default multiplayer PIE spawns `ServerLauncher` as a **separate child process** (`ProcessWatcher::LaunchProcess`, `.../Editor/MultiplayerEditorSystemComponent.cpp:341`), joined over loopback TCP (`:553-585`). In-process `editorsv_clientserver` exists but is **one world**: `IMultiplayer::StartHosting(isDedicated=false)` on the same singleton (`MultiplayerSystemComponent.cpp:387-418`, early-out if already hosting `:389-394`) — roles are per-entity, not two worlds. Two simultaneous `NetworkEntityManager`s: **not found**, blocked by the one-slot `AZ::Interface<T>`.
4. **Role/authority**: per-entity `NetEntityRole {Client,Autonomous,Server,Authority}` (`Gems/Multiplayer/Code/Include/Multiplayer/MultiplayerTypes.h:87-94`) on `NetBindComponent` (`.../NetBindComponent.cpp:722,752,755,789,792`); per-process `MultiplayerAgentType {Client,ClientServer,DedicatedServer}` (`Include/Multiplayer/IMultiplayer.h:45-51`).
5. **Dedicated server**: `Launcher.Static`/`.Headless.Static`/`.Server.Static` targets (`Code/LauncherUnified/CMakeLists.txt:25-84`) combine into `ServerLauncher`/`HeadlessServerLauncher` (`launcher_generator.cmake:12-24`); `.Headless` = same sources, one `O3DE_HEADLESS_SERVER=1` define, drops `NativeUI` (`Code/Framework/AzGameFramework/AzGameFramework/CMakeLists.txt:21,25-37`). Identical main loop across all launcher flavors (`Code/LauncherUnified/Launcher.cpp:83-125`).
6. **Hot reload**: no C++ module reload API — `ModuleManager` only load/unload (`AzCore/Module/ModuleManager.h:118,139-142`, despite a doc-comment claiming reload support). Lua scripts hot-reload (`AzFramework/Script/ScriptComponent.cpp:37,514-523`); new game code = process restart.

## 4. Flax Engine (`FlaxEngine/FlaxEngine`, `master` @ `82ee871`)

1. **Split**: one engine module (`BinaryModuleName="FlaxEngine"`, `Source/Tools/Flax.Build/Build/EngineModule.cs:42`). `FlaxGame` (standalone player) sets `IsMonolithicExecutable=false` (`Source/FlaxGame.Build.cs:20`) → engine becomes `LinkerOutput.SharedLibrary` + thin `FlaxGame.exe` (`EngineTarget.cs:108,147-235`); `FlaxEditor` stays monolithic (no `FlaxEngine.dll`). `FLAXENGINE_API` generated per binary module (`Builder.NativeCpp.cs:853,867,886,899,910`). Globals: `API_CLASS(Static)` classes (`Engine`,`NetworkManager`,`Level`), shared 1:1 with C#.
2. **Game unit**: one `Game` module by default, referenced by both `GameTarget`/`GameEditorTarget` (`Source/Editor/Editor.cpp:469-524`); always a shared library (`GameTarget.cs:17,40`). `Level` has one process-wide `Array<Scene*> Scenes` (`Source/Engine/Level/Level.h:24,41,46`) — no runtime "module instance" object.
3. **N worlds**: multiple additive `Scene`s, but `NetworkManager` is one static `Mode`/`Peer` (`Source/Engine/Networking/NetworkManager.h:60,65`) — client+server can't coexist with stock stack; `Host` mode is one peer as both roles over one scene set. PIE networking runs in-process (`Editor.OnPlayEnding()`→`NetworkManager.Stop()`, `Source/Editor/Editor.cs:678`); no `Process.Start` for PIE found.
4. **Role/authority**: per-process `enum NetworkManagerMode {Offline,Server,Client,Host}` (`NetworkManager.h:15-25`), set by `StartServer/Client/Host()` (`NetworkManager.cpp:508-589`). No per-entity role enum.
5. **Dedicated server**: no server target — normal player with `-headless` (`Engine::IsHeadless()`, `Source/Engine/Engine/Engine.cpp:422-425,698-707`) + `-null` (real `GPUDeviceNull`, `Source/Engine/GraphicsDevice/Null/GPUDeviceNull.h:17`, also the fallback when no GPU backend works, `Graphics.cpp:113-191`). No `FLAX_HEADLESS` build define found.
6. **Hot reload**: editor-only, round-trips through full scene unload/reload — `Scripting::Reload()` (`#if USE_EDITOR`, `Source/Engine/Scripting/Scripting.cpp:710-729`) refuses in-place reload while any scene is loaded, instead serializes all scenes to JSON, unloads/reloads assemblies, reparses (`Source/Engine/Level/Level.cpp:609-705,1740-1744`). Engine core and corlib refuse reload (`CanReload=false`, `Scripting.cpp:534,590-591`). Native game `.dll` mechanically follows the same `FreeLibrary`/reload path (`BinaryModule.cpp:1586-1593`); whether that's a hardened, documented C++ path is **not found**.

## 5. Stride (`stride3d/stride`, HEAD `a61e4033`)

1. **Split**: .NET assemblies (`Stride.Core*`, `Stride.Games`, `.Graphics`, `.Rendering`, `.Engine`), no export macros needed. No headless-without-graphics subset — `Stride.Games` hard-references `Stride.Graphics` (`sources/engine/Stride.Games/Stride.Games.csproj:20`).
2. **Game unit**: one `Game` model, instance-scoped systems (`sources/engine/Stride.Engine/Engine/Game.cs:33,38,43`); no singleton guard found. No client/server role split anywhere (no networking, see axis 4).
3. **N worlds**: not found — no listen/dedicated-server concept exists. Nothing structurally blocks two `Game` instances, but none observed; real multi-instance precedent is Live-Assembly-reload (axis 6).
4. **Role/authority**: not found — confirmed by absence (`grep -rln "NetworkManager|Multiplayer|Replicat" sources --include=*.cs` returns no engine-networking hits). No built-in multiplayer/replication layer.
5. **Dedicated server**: not found as a concept. `GameContextHeadless:GameContext<object>` (`sources/engine/Stride.Games/GameContextHeadless.cs:10-17`) is a windowless **client**, not a decoupled server build.
6. **Hot reload**: `LiveAssemblyReloader.Reload(...)` (`sources/engine/Stride.Debugger/Debugger/LiveAssemblyReloader.cs:19-33`) is a whole-assembly reload with a YAML entity-state round trip, but its body throws `NotImplementedException` at HEAD (line 33) — documented in source, not currently functional.

## 6. id Tech 4 / Doom 3 BFG (`id-Software/DOOM-3-BFG`, HEAD `1caba197`)

1. **Split**: monolith on PC — `Game-d3xp` is `StaticLibrary` on every PC config (`neo/game-d3xp.vcxproj`); no export macros in active use. `neo/_Dedicated.props` defines `ID_DEDICATED` but it's referenced nowhere in the tree.
2. **Game unit**: one game module (`d3xp`), a process-wide singleton: `idGameLocal gameLocal; idGame* game = &gameLocal;` (`neo/d3xp/Game_local.cpp:63-64`). `gameImport_t`/`gameExport_t` (`neo/d3xp/Game.h:329,337`) set engine pointers once even though the DLL-load path that would populate them is dead (axis 5).
3. **N worlds**: yes, for client+server — one shared `gameLocal` for both roles, computed live via `idCommonLocal::IsServer()/IsClient()` (`neo/framework/Common_network.cpp:93-102`), branched per-call e.g. `idGameLocal::MapRestart()` (`neo/d3xp/Game_local.cpp:1099-1106`). BFG's net stack is a lobby/session model (`neo/sys/sys_session_local.h`); the classic `idAsyncNetwork` split (`neo/framework/Async/`) is absent here and belongs to the non-BFG 2011 release, **not independently re-verified**.
4. **Role/authority**: per-process/session, via `idCommon` queries (`neo/sys/sys_session.h:256-258`) backed by `idLobbyBase::IsHost()/IsPeer()` (`neo/sys/sys_session_local.h:52-53`); game code branches `if(common->IsServer())` throughout `Game_local.cpp` (e.g. 1099,2274,3236) and `Player.cpp:6566`. No per-entity authority flag found.
5. **Dedicated server**: not found as a working PC path — `LoadGameDLL()` (`neo/framework/Common.cpp:819-873`) is wrapped in `#ifdef __DOOM_DLL__`, defined nowhere in the tree, so the DLL-load branch compiles out; no `com_dedicated`/`-dedicated`/null-renderer path exists anywhere in `neo/`. Classic `gamex86.dll`/`GetGameAPI` ABI is vestigial.
6. **Hot reload**: script/asset only, destroys map state — `Cmd_ReloadScript_f` (`neo/d3xp/gamesys/SysCmds.cpp:139-155`) forces a map exit; `reloadDecls`/`reloadImages` (`neo/framework/DeclManager.cpp:837`; `neo/renderer/ImageManager.cpp:675`) reload content in place. No C++ code hot-reload (module is statically linked).

## 7. Quake III Arena (`id-Software/Quake-III-Arena` @ `dbe4ddb1`)

1. **Split**: monolith engine (`quake3`/`q3ded`); game code splits into loadable **VM** modules (native DLL or `.qvm` bytecode) via one generic loader, `vm_t vmTable[MAX_VM=3]` (`code/qcommon/vm.c:43-44`). Each VM exposes one `vmMain()` entry (`code/game/g_main.c:203`) via `VM_Call()` (`vm.c:668-706`); globals crossing the boundary are limited to `currentVM`/`lastVM` (`vm.c:39-40`) — game state stays inside each VM's own memory.
2. **Game unit**: split **by role** into three VM singletons — `qagame` (server, `code/game/g_public.h:391-428`) as `vm_t *gvm`; `cgame` (`code/cgame/cg_public.h:74-236`) as `vm_t *cgvm`; `ui` (`code/ui/ui_public.h:37-189`) as `vm_t *uivm`. `VM_Restart` destroy-and-recreates, no per-world instancing.
3. **N worlds**: one shared world — listen server runs `SV_Frame()`+`CL_Frame()` from one `Com_Frame()` (`code/qcommon/common.c:2713,2754`) over an internal **loopback**: `"localhost"` trapped to `NA_LOOPBACK` (`code/qcommon/net_chan.c:702-711`); `SV_SpawnServer`→`CL_MapLoading()` connects the client to the just-started server (`code/server/sv_init.c:360-362`) via a `loopback_t loopbacks[2]` pair (`net_chan.c:572-607`).
4. **Role/authority**: per-process cvars `com_dedicated` (`code/qcommon/common.c:66,2404-2408`), `com_sv/cl_running` (`:2436-2437`); role separation in code is by **VM identity** (`g_*.c` only in server VM, `cg_*.c` only in client VM), not a runtime branch inside shared code.
5. **Dedicated server**: separate binary target — `code/unix/Makefile:249-256` builds `quake3`; `:289-334` builds `q3ded` with `-DDEDICATED -DC_ONLY`, swapping in null stubs (`null_client.o`,`null_input.o`,`null_snddma.o`, `Makefile:914-916`). `Com_Init()` also gates `CL_Init()` on `!com_dedicated->integer` (`common.c:2467-2473`).
6. **Hot reload**: `VM_Restart()` (`vm.c:355`) on `map_restart` (`code/server/sv_game.c:921-934`) reloads bytecode VMs in place ("leave everything else in place") but must fully free/recreate a native DLL VM (`vm.c:362-373`) — an explicit server-command boundary, server VM only.

## 8. Source SDK 2013 (`ValveSoftware/source-sdk-2013` @ `b8cfb12c`, `master`)

1. **Split**: game code only in this repo (`src/game/{client,server,shared}`); `engine.dll` is external. Visible split is a versioned string-interface ABI — `CreateInterface`/`InterfaceReg` (`src/public/tier1/interface.h:62-131`); `EXPOSE_SINGLE_INTERFACE_GLOBALVAR` exposes one versioned global per DLL: server `g_ServerGameDLL` (`src/game/server/gameinterface.cpp:561,564`, version `"ServerGameDLL012"`), client `gHLClient` (`src/game/client/cdll_client_int.cpp:756-759`, version `"VClient017"`). Engine singletons resolved individually per-DLL via `appSystemFactory` (`gameinterface.cpp:569-638`) — not shared memory.
2. **Game unit**: split **by role** into two DLLs from separate build projects — `server.dll` (`GAME_DLL` define, `src/game/server/server_base.vpc:65`), `client.dll` (`CLIENT_DLL`, `src/game/client/client_base.vpc:57`); `src/game/shared/` compiles into both. `g_ServerGameDLL`/`gHLClient` are file-scope compile-time singletons, one per DLL for its whole lifetime.
3. **N worlds**: not found in this repo (engine-side, external). Server code has essentially no rendering dependency — `IMaterialSystem` is only a bare forward decl, never dereferenced (`gameinterface.cpp:198`), vs. real materialsystem headers compiled into client (`client_base.vpc:985-1012`). `IsDedicatedServer()` (`src/public/eiface.h:108`) is *asked*, not decided, by server.dll (`gameinterface.cpp:520,634`); never called from `src/game/client/`.
4. **Role/authority**: structural (separate DLLs/source trees), not a runtime branch inside shared code — `src/game/shared/` is compiled twice, once per DLL.
5. **Dedicated server**: the `srcds` exe itself is engine-side, **not in this repo**. Compile-time role defines: `GAME_DLL` (`server_base.vpc:65`), `CLIENT_DLL` (`client_base.vpc:57`), `SWDS` for POSIX server builds (`server_base.vpc:67`).
6. **Hot reload**: not found — no reload mechanism in this repo; DLL loading is one-shot `DLLInit`/`Init`. Hammer "Run Map": no Hammer source in this repo; per Valve's public developer wiki (developer.valvesoftware.com, doc URL, not in this repo), Hammer launches the game exe as a **separate process** (`hl2.exe +map <name>`).

## 9. CryEngine V (`CRYTEK/CRYENGINE`, mirrored via `ValtoGameEngines/CryEngine` @ `d9d2c9f`; canonical repo no longer publicly cloneable per WebSearch, not independently re-verified)

1. **Split**: genuine per-domain DLLs (`CrySystem`,`CryAction`,`Cry3DEngine`,`CryAISystem`,`CryAnimation`,`CryAudioSystem`,`CryEntitySystem`,`CryNetwork`,`CryPhysics`,`RenderDll`/`XRenderD3D9`, etc.), each a `CryEngineModule(...)` CMake target (`Tools/CMake/CommonMacros.cmake:611-661`). Export macro: `CRYSYSTEM_EXPORTS→DLL_EXPORT / MONOLITHIC→empty / else→DLL_IMPORT` (`Code/CryEngine/CryCommon/CrySystem/ISystem.h:12-18`). Shared state: `extern SSystemGlobalEnvironment* gEnv` — a flat struct of ~45 raw interface pointers + flags (`bServer`,`bMultiplayer`) (`ISystem.h:729-819,1504-1509`), filled per-subsystem at module load (`pModule->Initialize(*GetGlobalEnvironment(),...)`, `ISystem.h:1459`); every DLL then reads `gEnv->pWhatever` directly (doc'd "faster than calling ISystem", `ISystem.h:725-728`).
2. **Game unit**: `CCryAction` (`CryAction.dll`) implements `IGameFramework`, a normal per-domain module, with a process-wide singleton pointer (`static CCryAction* m_pThis`, `Code/CryEngine/CryAction/CryAction.h:282,467`). Build system fatally errors if more than one game module is enabled without an override (`CommonMacros.cmake:672-675`) — one game module per binary enforced.
3. **N worlds**: Sandbox Ctrl+G "Game Mode" flips **one** shared world in place — `CGameEngine::SetGameMode()` (`Code/Sandbox/EditorQt/GameEngine.cpp:1000-1073`) sets `gEnv->SetIsEditorGameMode()` (`:1012`) and notifies the **same** `pEntitySystem`/`p3DEngine`/AI system/physical world (`:831,857,944,947,964,966`) — no second world/`gEnv` is ever allocated.
4. **Role/authority**: per-entity replication aspects `eEA_Script/Physics/GameClientStatic/GameServerStatic/GameClientDynamic/GameServerDynamic/...` (`Code/CryEngine/CryCommon/CryNetwork/INetEntity.h:36-60`) via `IEntityComponent::NetSerialize(ser,aspect,profile,flags)`. Canonical process-level check is the flat `gEnv->bServer` (`ISystem.h:800`; 5 guards in `Code/CryEngine/CryAction/CryAction.cpp:824,885,903,1143,1201`) — no per-entity `IsServer()` method found.
5. **Dedicated server**: distinct `DedicatedLauncher` target (`Code/Launcher/DedicatedLauncher/CMakeLists.txt:19-24`), gated by `OPTION_DEDICATED_SERVER` (`Tools/CMake/CommonOptions.cmake:41`) threading `-DDEDICATED_SERVER` into every module (`CommonMacros.cmake:651-756`). No `CryRenderNULL` module found in checkout — only `RenderDll/XRenderD3D9`; whether a null renderer is substituted is **not found**.
6. **Hot reload**: asset file-watching is first-class — `gEnv->pFileChangeMonitor` (`ISystem.h:742`); `ILiveCreate` on `gEnv` (`:763,784-785`). AI/flow-graph reload confirmed at the Game-Mode transition: `SaveAndReloadActionGraphs()`/`SaveAndReloadCustomActionGraphs()` (`GameEngine.cpp:849,854`). No DLL-level hot-swap found (the module-load path is a one-time boot call, `ISystem.h:1459`).

## The option space, as found

### (a) Engine/game code split shapes observed

- **Monolith, no module boundary.** Godot 4, Quake III's engine (client+server+renderer in one binary), id Tech 4 BFG (game module statically linked, DLL ABI dead), CryEngine's `OPTION_STATIC_LINKING=TRUE` build (forced on consoles, `CommonOptions.cmake:14-18`). CryEngine's own build treats dynamic per-domain linking as a **desktop dev-loop convenience**, not worth its cost elsewhere (`Configure.cmake:119-127`).
- **Per-domain engine DLLs + one shared mutable global struct.** CryEngine's `gEnv` (~20 DLLs, ~45 raw pointers). Trade-off stated by the source itself: the struct is a byte-identical layout every DLL must compile against (`ISystem.h:729`) — no versioned ABI between the DLLs themselves; one flag flip (`SetIsEditorGameMode`) reconfigures every subsystem at once. CryEngine's `OPTION_STATIC_LINKING_WITH_GAME_AS_DLL` hybrid (`CommonOptions.cmake:20`) is a tacit admission the two goals (swappable game code vs. minimal DLL overhead elsewhere) are in tension.
- **Static core framework + per-domain Gem DLLs, singletons shared via a named cross-DLL registry.** O3DE's `AZ::Environment`/`AZ::Interface<T>` — one slot per type per Environment (`Interface.h:26-32`). This is structurally why O3DE's default embedded-multiplayer story is a **separate process**, not two worlds in one — the registry has no room for two `IMultiplayer` instances at once.
- **One engine DLL, separate game module DLL(s), engine never role-split.** Flax: `FlaxEngine.dll` + `FlaxGame.exe`; game code is *always* a shared library even though the engine itself picks static-vs-dynamic per target.
- **Crate/assembly facade, feature-gated, no native DLL boundary by default.** Bevy (Cargo features) and Stride (.NET assemblies) both avoid the C++ DLL-ABI problem for default builds; re-introducing a real dylib boundary (Bevy's `dynamic_linking`, `hot_lib_reloader`) reintroduces the same class of hazard (`TypeId`/layout, README) independently derived in a different language.
- **Engine monolithic; game code split by ROLE into separate loadable modules, not by domain.** Quake III's `qagame`/`cgame`/`ui` VMs (3 fixed slots) and Source SDK 2013's `client.dll`/`server.dll` (2 DLLs, one external engine process, versioned `CreateInterface` ABI). Neither supports more than one simultaneous instance of a given role's module per process.

### (b) Client+server-in-one-process shapes observed

- **Always separate OS processes, host-side orchestrator spawns+connects them.** Godot's multi-instance/PIE (`OS::create_instance`) and O3DE's default multiplayer PIE (`ServerLauncher` child + loopback TCP). Trade-off: clean isolation (sidesteps every single-slot-singleton limit) at the cost of IPC/loopback overhead and two full process bring-ups.
- **One shared game-code singleton; role decided live per call, internal loopback network standing in for the wire.** id Tech 4 BFG's listen server (`gameLocal` shared, role queried from lobby state per call site) and Quake III's listen server (one VM pair, `"localhost"` trapped to an in-process loopback socket pair). Genuinely one world, zero duplication — but only because these are old, single-shared-simulation engines with no concept of client and server ever holding *different* scene state.
- **Two role-specific DLLs, both loaded by one external engine process; the engine decides the mode.** Source SDK 2013's `client.dll`+`server.dll`; `IsDedicatedServer()` is *asked*, not decided, by server.dll. Trade-off: shared source (`src/game/shared/`) compiled **twice** (once per DLL) for a hard client/server code separation.
- **One process-wide singleton mode-switches a single world in place; no second world is ever allocated.** CryEngine Sandbox Game Mode (flips `gEnv` state, notifies the same entity system/3D-engine/physics in place), O3DE's in-process `editorsv_clientserver` (1 `IMultiplayer`, roles per-entity), Flax's `Host` mode (1 `NetworkManager` over 1 `Level::Scenes`). Cheapest possible embedding (zero duplicated state), but caps out at "the host is also a client" — none of the three can hold two independently-ticked worlds at once, by construction of their singleton/registry layer.
- **N independent Worlds in one process via a lightweight per-World container, engine-provided and not render-specific.** Bevy's `App`/`SubApp` (doc'd for "processes... kept separate," used today for render extraction but generic). Yet lightyear's own "host-server" mode *deliberately collapses* what could be two Worlds (client app + server app) into one World with both plugin sets loaded, for a single authoritative state — the one engine found with a true N-Worlds-per-process primitive has its flagship networking user *not* using it for client+server-together, preferring one World with dual-role entities.
- **No built-in networking / not applicable.** Stride ships no client/server concept at all; one process, one world, no axis-(b) shape to report.
